## 2026-09-15
- Implemented M9 (auth + user sessions, T-050..T-060): `users` and `user_sessions` tables, bcrypt password login, DB-backed session cookie, and per-user scoping of decks, cards and settings. App is multi-user now; decks are private per owner.
- Ownership is checked once per request at whatever entry point first reads an id, then `deck_id` is trusted downstream. `GetDeckByID`/`GetCardByID` fold "not yours" into `sql.ErrNoRows` so handlers 404 without leaking whether the id exists — no separate 403 path.
- Reviewing the plan against the code first turned up three things worth the delay: `SubmitAnswer` discarded its deck param and `EndSessionEarly` never had one, so both accepted a body-supplied `session_id` for anyone's session (fixed with `GetSessionByID(db, deckID, id)`); `SetSetting`'s `ON CONFLICT(key)` would have failed at runtime, not compile time, under the new composite PK; and SQLite's `UNIQUE` on TEXT is case-sensitive, so `email` needed `COLLATE NOCASE` plus lowercasing on write.
- Scoped `UPDATE`/`DELETE` now check `RowsAffected` — a zero-row write returns nil error in `database/sql`, which would have flashed "Saved." for a deck the user doesn't own.
- `schema.sql` is `CREATE TABLE IF NOT EXISTS` only and cannot add `decks.user_id` to an existing DB, so `db.Open` checks `PRAGMA table_info(decks)` *before* applying the schema and refuses to start with "run `task db:reset`". Without the pre-check the failure surfaced later as `no such column: user_id` from an index creation.
- E2E: one shared logged-in browser context created in `TestMain` keeps all 24 pre-auth cases unchanged; new `cases/auth.go` covers register/logout/wrong-password/case-insensitive login/protected-route redirect plus a two-user deck privacy check. Two selector collisions had to be resolved — the nav logout button matched page-wide `button[type=submit]` (dropped the explicit attribute, submit is the in-form default) and `querySelector('form')` started resolving to the nav form (scoped to `main form`).
- CSRF is still just `SameSite=Lax`; login has no rate limiting and registration is open. Deliberate for this stage, listed in the architecture doc's known gaps.
- Restyled the whole UI as a TUI theme on the Tokyo Night palette. The aesthetic is a fit rather than a costume: server-rendered, no-JS, form-driven — a terminal look is honest about what the app is. Ground rules are written at the top of `style.css` so later edits stay coherent: monospace throughout, no border radius, tokens for size and spacing.
- All ornament (button brackets, row markers, the flashcard cursor) lives in `::before`/`::after`, never in markup. That rule is load-bearing for the e2e suite, not just taste: Playwright reads `textContent`, which excludes pseudo-elements, so decoration cannot break an assertion on `.mc-option` or `.front-text`. Nothing in the templates changed for the sake of looks — the deck-card title inset into its own top border is the existing `<h2>`, positioned.
- Theme switching is a cookie, not a `settings` row, despite the per-user key/value store already existing. Two reasons the settings table loses: the theme must be known before the first byte of HTML or the page paints in the wrong palette, and it has to work on `/login` and `/register`, where there is no user to look a setting up for. `render` stamps `<html data-theme>`, so there is no flash and no JavaScript. Three states, so "follow my OS" stays reachable after picking a fixed theme — a two-way toggle strands the user.
- The light palette is written out twice on purpose: once under `prefers-color-scheme` guarded by `:not([data-theme="dark"])`, once under `[data-theme="light"]`. Without that guard a user on a light OS who picks dark is overridden by their own system setting. No build step here, so the duplication can't be factored out.
- `currentTheme` whitelists to `dark`/`light`. The cookie is attacker-controllable and its value is interpolated into an HTML attribute, so `html/template` escaping is the backstop, not the control.
- Mutation testing earned its keep: deleting that whitelist left the e2e suite green. The hostile-cookie case used a raw `" onload="alert(1)` payload, whose quotes and spaces are illegal in a cookie value — the browser never sent it, `c.Cookie` errored, and the case passed for entirely the wrong reason. Percent-encoding it makes it legal on the wire and `c.Cookie`'s `url.QueryUnescape` decodes it back at the handler. The comment records why, so it doesn't get "simplified" into a no-op again.
- Three real bugs surfaced while restyling, all predating this work: `card.js` set inline `style.display`, which outranks the stylesheet and made the flashcard reveal impossible to style or animate (now one class toggle, CSS owns the rest); `input[type=email|password]` were never styled because the selector list only covered `text`/`file`, so login and register rendered browser-default; and `.card-table` in `session_summary.html` had no CSS at all.
- Every mutation being POST + redirect means each answered card is a full page load. `@view-transition { navigation: auto; }` cross-fades those natively — one CSS line, no JS, silently ignored by browsers that lack it. Considered HTMX and rejected it for now: exactly one interaction suffers from full reloads, which doesn't justify a dependency plus a second response path per handler.
- Theme e2e cases each build their own browser context. The theme is a cookie, so sharing `configuration.Context` would leak one case's choice into the next and make test ordering significant.
- Flattened every function at nesting depth 3 into guard clauses (`render`, `NewDeckForm`, `StartSession`, `SubmitAnswer`, e2e `AnswerMC`). Measured with a throwaway `go/ast` walker rather than by eye, which is also how "zero functions at depth ≥ 3" stays checkable later. Two real defects fell out of the extractions: `NewDeckForm` did an unchecked `v.(AIFormData)` on a `pending` map shared with the CSV import flow, so replaying an import token on the AI form panicked; and `SubmitAnswer` guarded `rating >= 0 && rating <= 3` after already clamping to that range, so the "Unknown" label branch was unreachable.
- Audited the API key path before putting a real key in it. Storage is plaintext in `settings`, but exposure is contained: the key is never rendered back (only a `HasAPIKey` boolean), gin logs method/path not bodies, and provider error bodies are capped at 200 bytes. Four defects around it were worse than the storage: the error from `DeleteSetting` was dropped so a *failed* key-clear still flashed "Settings saved."; submitting a new key while ticking "Clear saved key" wrote it and then deleted it, silently discarding what was typed; the `SetSetting` failure paths reported `HasAPIKey` from the submitted field rather than from storage, so a transient failure made an existing key look absent; and base URL/model were trimmed before validating but not before storing, so a trailing space survived into every request.
- `LLM_API_KEY` overrides the stored key and is never written to the DB. `SettingsPage` deliberately reports what is *stored* rather than what is *effective*, or the "Clear saved key" box would appear for a key that lives only in the environment.
- Provider presets (`internal/ai/presets.go`) exist because the free options were reachable but not discoverable: configuring an LLM meant knowing a base URL and an exact model id. A preset carries label, base URL, default model, whether a key is needed, and where to get one, so picking "Google Gemini (free tier)" leaves exactly one field to fill. `ai.New` resolves client and key requirement from the table instead of a hand-maintained switch, so adding a provider is a table entry.
- Prefill is server-side — `SaveSettings` falls back to the preset when a field is blank, and `SettingsPage` renders a pristine form already filled. `static/settings.js` only refills on *change*, and restores the user's own values when they switch back to their configured provider, so browsing the list cannot destroy a working setup. With JS off the same defaults still apply on save; the enhancement is never load-bearing.
- Presets deliberately do not lock anything: base URLs and model ids drift and there is no mechanism to push updated defaults to a running install, so every field stays editable. That risk landed on the first real use — the prefilled `gemini-2.0-flash` was already stale and had to become `gemini-3.6-flash`. Treat the other providers' defaults as equally suspect.
- `SettingsValidation` used to assert that an untouched form errors with "required". Presets make that submission succeed by design, so the case was retargeted at Custom, where nothing can supply the values and the rule still holds; `PresetSaveNeedsOnlyAKey` covers the other side and blanks the fields deliberately to exercise the no-JavaScript path.
- `Ping` sent a real completion with a 5-second budget. LM Studio and Ollama load weights lazily, so the first request after startup spends tens of seconds paging gigabytes off disk and blew that deadline — Test Connection reported "connection failed" for a correct configuration, then succeeded on a second press because the failed attempt had started the load. It now asks `GET /models` first: instant, loads nothing, and still proves server reachable, base URL right, key accepted. Servers without `/models` fall back to the completion ping at 60s, that being exactly the path that may wait out a cold load.
- The `/models` listing also catches a wrong model id at Test Connection instead of as a 404 three minutes into a generation. It is a warning, not a failure — the server answered and took the credentials, and some servers accept ids they do not advertise, so it must never block a configuration the user insists on. `ModelNotListedError` keeps that distinguishable by the handler rather than flattened into an error string, which matters more once an agent is reading it instead of a person.
- `internal/ai/live_test.go` is an opt-in integration test (skipped unless `LIVE_LLM_BASE_URL` is set) that runs the real `GenerateCards` path and asserts the cards parse and carry the `(translation)` example format. The other AI tests mock the transport, so nothing covered the thing most likely to break in practice: whether a given model returns JSON this app can use. Verified against LM Studio with qwen3.8-27b — 5/5 cards, correctly formatted; 10 cards took 66s, so the 3-minute `GenerateCards` ceiling allows roughly 30 before generations start being cut off.
- Mutation testing earned its keep twice more. The API-key clear path had no coverage at all, which is why the dropped `DeleteSetting` error survived; and reverting `Ping` to completion-only correctly fails the new cases. Worth keeping the habit: assert a new test fails without the fix before believing it.

## 2026-09-26
- Replaced "refuse to start, run `task db:reset`" with versioned migrations. Production crash-looped on its pre-auth database after the auth image shipped: the refusal was correct, but a reset is only an answer while there is nothing to lose. Hand-rolled rather than goose/golang-migrate: one SQLite file, one replica, migrate-at-startup, and the nightly backup CronJob is the rollback story, so a library's down-migrations and CLI buy nothing. It is one file over `PRAGMA user_version` plus embedded `migrations/NNNN_*.sql`; the version sits in the file header and commits atomically with each migration, so there is no version table to drift or "dirty" flag to clear by hand.
- Baselining: every pre-migrations database reports `user_version` 0. One with `decks.user_id` ran the full post-auth `schema.sql` on every start, so it is recorded at 3; anything else starts at 0. `0001_initial.sql` keeps `IF NOT EXISTS` for exactly that reason — on a pre-auth database it is a no-op that only fills in tables an older build hadn't created. The first test run caught the baseline being detected but never written, which would have left `0004` with nothing to count from.
- `0003` rebuilds `decks` and `settings` (SQLite can't `ADD COLUMN ... NOT NULL REFERENCES` or change a primary key). With foreign keys on, `DROP TABLE decks` cascades and silently deletes every card and study session — the pragma is ignored inside a transaction, so each migration switches it off on a pinned connection, runs in a transaction, and asserts `PRAGMA foreign_key_check` before commit. Mutation-checked: leaving foreign keys on makes the card-survives test fail.
- Orphan decks get an owner from `MIGRATE_OWNER_EMAIL`/`MIGRATE_OWNER_PASSWORD`, created in a Go `prepare` step (bcrypt can't be done in SQL) and handed to the SQL through `temp.migration_owner`. No decks → no owner needed, and pre-auth settings (LLM keys, re-enterable) are dropped with a log line rather than assigned to a guess. Each migration commits alone, so a missing variable fails `0003` while leaving `0001`/`0002` applied and the data intact; the next start retries.
- Found on the way: `db.Open` ran `PRAGMA foreign_keys = ON` via `Exec`, which only reaches one connection in `database/sql`'s pool — the others ran without cascades. Now in the DSN; the new test holding three connections at once fails on connections 1 and 2 when the DSN pragma is removed, reproducing the old behaviour exactly.
- Account menu + profile section. The nav's Settings link, email and Log Out collapsed into one dropdown built on native `<details>`/`<summary>`: the browser owns open/close and keyboard handling, so it works with JS off; `static/menu.js` only adds close-on-outside-click and Escape, which the element lacks. Everything account-related now lives under `/profile` with a shared side menu (Account · Security · AI Provider), and the dropdown itself holds only Profile and Log Out so there is one way in; the LLM settings page moved to `/profile/ai` unchanged, with `/settings` 301-redirecting for bookmarks. The side menu is an `<aside>`, not a `<nav>` — the global `nav` rule is the header bar's, and `nav a:has-text(...)` e2e selectors would have matched it too.
- Security page: change password, sign out everywhere else, delete account. Both password change and delete re-ask for the current password even though the user is logged in — a borrowed or stolen session alone must not be enough to lock the owner out or wipe their data. A password change ends every other session (the one making the change stays), mutation-checked by dropping that call. Register and change share `newPasswordProblem`, and Login/change/delete share `passwordMatches`, so the rules can't drift apart.
- `users.display_name` is migration `0004`, the first real use of the new runner: a plain `ADD COLUMN ... NOT NULL DEFAULT ''`, no rebuild needed. All four user-loading queries now go through one `userColumns`/`scanUser` pair, since each new column previously meant editing four SELECTs. The baseline test had to wind its fixture back (`DROP COLUMN display_name`) to stay a faithful pre-migrations database once `Open` itself produced version 4.
- Delete account relies entirely on `ON DELETE CASCADE` from `users` (sessions, settings, decks → cards, study sessions, answers); `TestDeleteUserCascades` pins that, which matters more now that foreign keys are actually on for every pooled connection.
- SRS vs Linear looked identical in use, and for a fresh deck they were: a new card is both due today and never-passed, so both queues picked the same cards in the same order. They only diverged after a session, and Linear's divergence was a bug against its own spec ("sequential, unlearned cards first"): it studied *only* never-passed cards, so every card rated Good or Easy left linear study permanently and a finished deck said "All cards have been studied" forever. `GetLinearCardIDs` now returns every card — unlearned first in insertion order, then learned cards by due date. Ordering the learned tail by due date makes the deck rotate on its own, since each review pushes a card's due date out; ordering by id would have replayed the same first 20 of a large deck every time.
- Kept both modes rather than collapsing to SRS-only, but made the difference visible: a shared `_mode_picker` partial (replacing two copies of the radio markup) describes each mode where it is chosen, the deck page names the mode, and an empty SRS session now dates the next review and points at Linear for anyone who wants to keep going. Both modes still grade through SM-2, so switching is lossless.
- The first version of the linear e2e case passed against the bug. It imported `spanish_verbs.csv` — 25 cards against a 20-card linear session — so the "second session" still had unseen cards regardless of the fix. It now uses the single-card fixture, and fails with the old query. Same lesson as before, caught by the same habit: make the test fail without the fix before trusting it.
- `RateAllFlashcards` needed `ExpectNavigation` despite the deprecation notice: the next card lives at the identical `/session` URL, so `WaitForURL` returns before the redirect and the loop reads the previous page. Clicking inside the callback is the race-free use.
- Again/Hard/Good/Easy were near-meaningless in use. Plain SM-2 maps them to quality 0/2/4/5 and fails anything below 3, so **Hard was a failure** — it reset the card exactly like Again and scored ✗ — while Good and Easy gave the same 1-day then 6-day gaps and differed only in the ease multiplier, first visible on the third review. Nothing on screen said any of this. Rewrote `srs.Update` as SM-2's shape with Anki's semantics: Hard is a pass with ×1.2 growth (never shrinking the gap), Easy stretches by ×1.3, ease moves −0.20/−0.15/0/+0.15, and each button's gap is forced at least a day past its left neighbour so rounding can never make two buttons show the same number. Existing cards keep their stored interval and ease; only future reviews follow the new rules.
- `srs.Preview` computes the four gaps without mutating; the buttons display them ("soon · 1d · 2d · 4d" on a new card) and `Update` takes its interval from `Preview`, so the label and the schedule cannot drift — `TestPreviewMatchesUpdate` pins that.
- Again now re-queues the card at the end of the session via `json_insert(card_queue, '$[#]', ?)` — one statement, no read-modify-write of the JSON queue — capped at 3 appearances per card so a card you keep failing can't hold the session hostage. Multiple choice gets the same treatment (a wrong pick is Again). Two knock-on effects: the summary's missed list showed one row per wrong *answer*, so a thrice-missed card appeared three times (now one row per card, first miss kept); and `SummaryMissedCards`, which answers a 25-card deck all wrong, now runs 75 answers and outgrew the old 55-click loop bound. Both requeue and dedupe were mutation-checked against their e2e cases.
- AI tutor (M10, phase 1 of the assistant): "Ask the tutor" on a card — after reveal, on MC feedback, and in the deck's card list — opens a per-card conversation with preset questions (Explain, More examples, Memory trick, Quiz me) and free text, using the learner's own configured provider. Phase 2, the card-maintenance agent with tools and Propose + Apply, is planned in `docs/plans/ASSISTANT_AGENT_PLAN.md` rather than built.
- Streaming without JavaScript. The user ruled out client JS even for live replies (and floated NATS). NATS moves messages between server processes and never reaches the browser, so it was the wrong layer; the browser half is solved by streaming HTML: the GET writes the page's top half, flushes, writes each chunk HTML-escaped and flushed, then the bottom half. Browsers render HTML as it arrives. The template is split into `tutor_top`/`tutor_bottom` (the top ends *inside* the reply element), written via the engine's `HTMLRender.Instance(...).Render` so gin's debug-mode template reloading still applies. POST + 303 is preserved: the POST only starts the work.
- Generation is detached from the request — its own 3-minute context in a goroutine — and publishes to `internal/stream`, a `Broker` interface with an in-memory implementation; that interface is where NATS JetStream would go for multiple replicas. The broker is a growing buffer plus a "changed" channel closed and replaced on every write, not per-subscriber channels: a slow reader can neither block the producer nor miss text, a late reader (page reload) replays from the start, and there is nothing to leak. A reply stuck `generating` with no producer (server restart) is marked interrupted on the next view instead of hanging forever.
- The finished-reply cursor had a subtle problem: the streaming element's class is already sent and cannot be changed, so a CSS cursor on `.tutor-streaming` would blink forever. `tutor_bottom` appends an empty `.tutor-done` marker inside the text and `:has(.tutor-done)` switches the cursor off — content can still be added after the fact even when attributes can't.
- The e2e suite runs a fake OpenAI-compatible server that sends its first chunk, pauses 1.5s, then finishes. `TutorStreamsReply` asserts the first chunk is on the page *while* the end marker is absent — mutation-checked by buffering the whole reply in the handler, which fails it with "the page was not streamed". It also pins escaping: the fake reply contains `<b>bold</b>`, which must render as text.
- Conversation history sent to the model skips failed replies, trims to 20 turns, and merges consecutive user turns — some providers reject two user turns in a row, which a failed reply leaves behind. The first version merged *before* appending the new question, so the orphan still preceded it; the tutor test caught that. A trim can also leave the history starting with an assistant turn, which Anthropic rejects, so that is dropped too.
- `TestOpenBaselinesPostAuthDB` broke again on the new migration because its fixture built the latest schema and undid later migrations by hand. It now builds the fixture with `migrateTo(authVersion)`, so it stays correct as migrations are added.
- Not verified against a real model in this session: no local LLM server was running. `internal/ai/live_test.go` gained `TestLiveChat` (opt-in via `LIVE_LLM_BASE_URL`), which also fails if a reply arrives in a single chunk, i.e. was not actually streamed.

## 2026-09-27
- "Create with AI" is now an interview instead of a form: the deck builder asks, one short question at a time, for language, purpose/level, topic and size, then the learner presses **Create deck**. The conversation is summarised into a spec (name, language, generation prompt, count) by one extra non-streamed call, and the old AI form — unchanged fields, still posting to `/decks/new-ai` — becomes the pre-filled, editable **review step**. Opening the old form with nothing to review now redirects to the assistant. Generation, the processing page and the result are untouched.
- Why the learner, not the model, ends the interview: a model deciding "I have enough" (via a tool call or a magic JSON marker) needs tool support or reliable formatting, and small local models manage neither well. A button plus a separate summarisation call works with any model and keeps the human in control; the review form is the same Propose + Apply idea phase 2 uses for card edits, applied to a whole deck. The model is told it cannot create the deck and should say when it has enough.
- The builder's greeting is page text, not a model turn: the first question never varies, so asking a model for it would cost a call and a wait. The system prompt quotes it so the model knows what the learner's first message answers, and the summary transcript prepends it.
- Generalised rather than copied: the tutor's tables became `conversations` (kind `tutor` | `deck_builder`, partial unique indexes enforcing one tutor chat per card and one open builder per user) and `conversation_messages` (migration `0006`, carrying existing tutor rows over with their ids — tested). `internal/tutor` became `internal/assistant`: `Ask` takes the system prompt and an `open` function that creates the conversation only once the question is known answerable, so an unconfigured user leaves nothing behind. The streaming page logic moved to `renderChat` with shared `_chat_open`/`_chat_close` partials; the tutor and the builder are now just two prompts and two templates.
- `AIExecute` still had an unchecked `v.(AIFormData)` on the pending map shared with CSV import — the same panic already fixed in `NewDeckForm`, surviving one handler over. Both now go through `pendingAIForm`. The spinner page became generic (message + next URL, still a meta refresh) so "summarising…" and "generating…" share it.
- The e2e fake LLM routes by system prompt. The first run failed because the summary prompt mentions "a flashcard generator" and the fake matched the card-generation branch first, returning a card array; the real parser correctly rejected it as not a spec. Matching order fixed in the fake, and the failure mode was reassuring: a wrong-shaped answer produces a "could not summarise, try again" flash rather than a bad deck.
- The deck builder's review form was one screen too many: after the interview, Create deck → spinner → the old form, pre-filled → Generate again. The chat had already built the deck, so the plan now appears *in the chat*: when the assistant knows language, level, topic, size and study mode, it ends its reply with a ` ```deck {json} ``` ` block, which the page shows as a card with **Generate Deck**. Changes are made by talking ("make it 30 cards") — the assistant replies with a new, complete block, the newest card is the live one and older cards show as superseded. The old AI form, its handler and its route are gone; `/decks/new?ai_mode=true` redirects to the assistant for bookmarks, and generation errors return to the chat with a flash.
- This reverses part of yesterday's reasoning ("the model shouldn't decide when it's done"): the model now emits the plan itself. It is safe to rely on because it is no longer the only path — Create Deck Plan stays as a fallback for models that never write the block, running the old summary call and storing its result *as a plan message*, so both routes end in the same card. And the Generate form posts only the message id: the server re-reads the plan from the learner's own conversation and refuses anything but the newest, so a stale card on screen can't generate a superseded plan and nothing about the deck is trusted from the browser.
- Hiding the block while it streams: `assistant.PlanFilter` sits between the broker and the page, passing text until the marker and nothing after. A stream can split the marker across chunks ("``" then "`deck"), so the filter holds back any tail of the text that could be the start of the marker until the next chunk decides it, and `Flush` releases it at the end — ASCII-only marker, so the cut never splits a UTF-8 character. `ExtractDeckPlan` applies the same rule to stored replies (hidden from the *first* marker, plan from the *last* block) and a test checks the streamed view equals the stored view, so a reload never shows different text. Mutation-checked: streaming unfiltered chunks leaks the JSON and fails `DeckBuilderPlanInChat`.
- The plan's card for a reply that has only just finished streaming isn't known when the top half of the page is sent. After the stream ends, `renderChat` re-reads the reply (saved before the broker's Finish) and hands its card to the bottom half — `ChatData` is passed by pointer so it can be filled in mid-render.
- A test failure worth remembering: the fake's plan reply had no pause, so it was *finished* before the browser followed the redirect and the page rendered from the database without streaming — correct app behaviour, wrong test assumption. The fake now pauses before the block, so the split marker genuinely streams through the filter in a real browser.
